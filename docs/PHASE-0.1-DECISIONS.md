## A. Task Tracker: интеграция при полном доступе к коду сайта

Это меняет дизайн: раньше мы подстраивались под чужой API, теперь проектируем его правильно с обеих сторон.

### A.1 Правило безопасности изменений сайта

Вы просили сначала показывать изменения — фиксирую это как процесс, обязательный для всех фаз:

1. **Сначала я читаю репозиторий сайта** и составляю `docs/tracker/CHANGE-PLAN.md`: полный список файлов (новые / изменённые), все миграции БД, все новые маршруты, оценка влияния на существующий функционал.
2. **Только аддитивные изменения.** Ничего не удаляется, не переименовывается, существующие маршруты, модели, шаблоны и ответы API не меняются.
3. **Изолированное пространство имён** — все новые маршруты под префиксом `/api/atlas/v1/*`. Пересечение с существующими URL исключено.
4. **Миграции только additive** (новые таблицы, новые nullable-колонки), каждая с рабочим `down`. Никаких `DROP`, `ALTER TYPE`, `NOT NULL` на существующих колонках.
5. **Feature flag** `ATLAS_INTEGRATION_ENABLED` (по умолчанию `false`): выключен — новые маршруты отдают 404, триггеры/хуки не выполняются, сайт ведёт себя ровно как сейчас.
6. **Прогон существующих тестов** до и после; если тестов нет — фиксирую вручную проверенный чек-лист ключевых сценариев сайта.
7. Работа в отдельной ветке, отдельный коммит на каждую логическую единицу, откат тривиален.
8. **Вы утверждаете CHANGE-PLAN → только потом я пишу код.**

### A.2 Аутентификация: варианты и рекомендация

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| Статический API-ключ (Bearer) | 15 минут работы | Долгоживущий секрет, лежит на обеих сторонах; утечка БД сайта = полный доступ; нет защиты от replay; светится в логах | ❌ |
| HMAC-SHA256 (общий секрет) | Просто, есть везде, защита от replay и подмены тела | Общий секрет: компрометация сайта = возможность подделать запросы к ATLAS | 🟡 запасной |
| OAuth2 client_credentials | Стандарт | Нужен token endpoint, хранение токенов, ротация — избыточно для одного клиента | ❌ |
| mTLS | Сильнейший транспортный уровень | Управление сертификатами; ломается на многих PaaS/CDN, которые терминируют TLS | 🟡 доп. слой |
| **Асимметричная подпись (Ed25519), обе стороны** | На сайте лежит только **публичный** ключ ATLAS — утечка БД сайта не даёт подделать запросы; ротация по `kid`; защита от replay и от подмены тела | Нужна библиотека Ed25519 на стороне сайта (есть везде: PyNaCl, `sodium`, `tweetnacl`, Node `crypto`) | ✅ **рекомендую** |

**Рекомендуемая схема — асимметричная в обе стороны:**

*ATLAS backend → сайт:*
```http
POST /api/atlas/v1/tasks
Authorization: Bearer <JWT, alg=EdDSA, exp = now+60s>
Content-Digest: sha-256=:<base64>:
Idempotency-Key: 01J8...
```
JWT-claims: `iss=atlas-backend`, `aud=tracker`, `sub=<user_id>`, `iat`, `exp` (60 с), `jti` (одноразовый), `bh` (SHA-256 тела).
Сайт проверяет: подпись публичным ключом по `kid` → `exp` → `aud` → `jti` не использован (кэш 5 мин) → `bh` совпадает с телом. **Сайт не хранит ни одного секрета ATLAS.**

*Сайт → ATLAS (webhooks):* зеркально. У сайта своя пара ключей, ATLAS хранит его публичный ключ.
```http
POST https://atlas.<домен>/v1/integrations/tracker/webhook
X-Atlas-Signature: v1=<base64(ed25519(timestamp || "." || body))>
X-Atlas-Timestamp: 1786...
X-Atlas-Delivery-Id: 01J8...
```
Допуск по времени ±300 с, кэш `delivery_id` против повторов.

**Дополнительные слои:** TLS 1.3 обязательно; IP-allowlist статического адреса VPS на стороне сайта; отдельная машинная идентичность — ATLAS **никогда** не переиспользует пользовательские сессии/куки сайта; ротация ключей без простоя (сайт хранит несколько активных `kid`).

*Запасной вариант:* если Ed25519 на стеке сайта окажется неудобен, тот же протокол работает на HMAC-SHA256 с разными секретами по направлениям — адаптер поддержит оба, выбор в конфиге. Но по умолчанию идём на асимметрию.

### A.3 Realtime вместо polling — и почему один webhook всё же недостаточен

Основной канал — **webhook** (сайт → ATLAS, push при каждом изменении). Но webhooks доставляются at-least-once и теряются при даунтайме ATLAS, деплое или сетевом сбое. Поэтому:

**Webhook + change feed + reconcile:**
- **Webhook** — мгновенная реакция (типично < 1 с).
- **Change feed** `GET /api/atlas/v1/changes?since=<cursor>` — монотонный курсор, отдаёт только новое. Когда изменений нет, ответ пустой и почти бесплатный.
- **Reconcile** — вызов change feed раз в 15 минут и **всегда** при переподключении/старте backend. Это не polling ради данных, а сверка на случай потерянного события. Без неё система рано или поздно тихо рассинхронизируется.

Ретраи на стороне сайта: экспоненциальный backoff (1с, 5с, 30с, 2м, 10м), после 6 неудач — в `atlas_webhook_deliveries` со статусом `dead`, и reconcile всё подберёт.

Идемпотентность: у каждого события `event_id`; ATLAS хранит обработанные ID. Повторная доставка — no-op.

*Альтернатива, если у сайта уже есть realtime-инфраструктура (SSE/WebSocket):* можем подписаться на существующий поток вместо webhook. Решим после чтения репозитория — webhook выбран как вариант, не требующий от сайта ничего, кроме исходящего HTTP.

### A.4 Предлагаемые эндпоинты сайта (`/api/atlas/v1/*`)

```
GET    /health                          — версия схемы, флаг интеграции
GET    /changes?since=<cursor>&limit=   — ★ change feed, основа синхронизации

GET    /tasks?status=&due_from=&due_to=&updated_since=&limit=&cursor=
POST   /tasks                           — Idempotency-Key обязателен
GET    /tasks/{id}
PATCH  /tasks/{id}                      — статус, приоритет, дедлайн, заголовок
DELETE /tasks/{id}                      — soft delete

GET    /goals ; POST /goals ; PATCH /goals/{id}
GET    /goals/{id}/progress

GET    /schedule?from=&to=              — события расписания и дедлайны
POST   /schedule ; PATCH /schedule/{id}

PUT    /reports/daily/{date}            — upsert отчёта от ATLAS
GET    /reports/daily/{date}

PUT    /analytics/activity/{date}       — суточные агрегаты активности
GET    /analytics/summary?from=&to=
```

Все мутирующие — с `Idempotency-Key` (повтор возвращает тот же результат, не создаёт дубль). Все ответы — с `updated_at` и `version` для разрешения конфликтов.

## B. Voice Engine: заменяемый STT, автоопределение языка, code-switching

### B.1 Контракт провайдера

STT изолирован за одним интерфейсом; ни Whisper, ни облако не «зашиты» никуда:

```python
class STTProvider(Protocol):
    name: str
    languages: frozenset[Language]
    supports_streaming: bool
    supports_auto_detect: bool
    supports_biasing: bool          # hotwords / phrase list

    async def transcribe(
        self,
        audio: AsyncIterator[AudioChunk],   # 16 kHz mono PCM
        hint: TranscriptionHint,            # ожидаемые языки, словарь терминов, контекст
    ) -> AsyncIterator[TranscriptionEvent]  # partial → final
```

`TranscriptionEvent.final` содержит: `text`, `language`, `language_confidence`, `avg_logprob`, `words[]` (с таймингами, где провайдер отдаёт), `provider`.

Аналогично устроены `TTSProvider`, `WakeWordProvider`, `SpeakerVerifier`, `LLMProvider`. Замена любого — правка YAML-конфига, не кода.

### B.2 Варианты STT и рекомендация по языкам

| Провайдер | ru | en | kk | Стриминг | Где | Комментарий |
|---|---|---|---|---|---|---|
| **faster-whisper `large-v3-turbo`** (int8, CUDA) | отлично | отлично | слабо | псевдо (чанки) | локально, ~1.5–2 ГБ VRAM | **Основной для MVP.** Аудио не покидает ПК, задержка минимальна |
| faster-whisper `medium`/`small` | хорошо/средне | отлично | плохо | псевдо | локально, 0.5–1.2 ГБ | Запас, если GPU занят |
| **Azure Speech** | отлично | отлично | **есть `kk-KZ`** | настоящий | облако | Есть **continuous language identification** — распознаёт смену языка внутри потока. Лучший вариант для kk и для code-switching |
| Google Cloud STT (Chirp) | отлично | отлично | **есть `kk-KZ`** | настоящий | облако | Альтернатива Azure; auto-detect по списку кандидатов |
| Whisper, дообученный на казахском (KSC) | — | — | заметно лучше базового | псевдо | локально | Путь к качественному kk без облака; требует проверки на ваших данных |
| Vosk | средне | средне | ограниченно | да | локально, CPU, ~50 МБ | **Офлайн-деградация**, когда нет интернета и нет GPU |

**Политика маршрутизации (`stt_routing.yaml`, редактируется без пересборки):**

```yaml
default: local_whisper_turbo
rules:
  - when: {lang_hint: kk}            use: cloud_azure
  - when: {detected_lang: kk, confidence: ">0.6"}  use: cloud_azure   # реранскрипция
  - when: {gpu_free_vram_mb: "<1800"}              use: cloud_azure
  - when: {network: offline}         use: vosk        # с предупреждением в UI
fallback_chain: [local_whisper_turbo, cloud_azure, vosk]
```

Итог: **ru/en в MVP — локально на вашей 3060, без облака и без задержки сети. Казахский — облако, включается позже, не блокируя MVP.** Ровно как вы просили.

### B.3 Автоопределение языка — три слоя

1. **Приор** — `primary_lang` пользователя + язык последних N реплик (липкость сессии). Не даёт «дрожания» на коротких фразах.
2. **Акустический** — Whisper `detect_language` по первым 2–3 секундам (отдаёт распределение вероятностей) либо непрерывный LID у Azure.
3. **Текстовый** — быстрый LID (`lingua-py`/fastText) по финальному транскрипту. Если он резко расходится с акустическим и общая уверенность низкая — одна реранскрипция с исправленной подсказкой (только для коротких/критичных реплик, чтобы не терять время).

**Анти-флаппинг:** смена языка сессии происходит, только если уверенность > 0.85 **или** две подряд реплики на новом языке. Односложные «да», «yes», «ок» язык не переключают никогда.

### B.4 Code-switching — где он реально ломается и что с этим делать

Ваши команды почти всегда смешанные: «Atlas, открой **VS Code** и запусти **dev server**», «добавь задачу закончить **Windows Agent**». Это самый частый и самый недооценённый источник ошибок.

Четыре механизма, все провайдеро-независимые:

1. **Доминирующий язык, а не принудительный.** Языку выставляется значение по основной массе фразы; Whisper при этом корректно оставляет английские технические термины латиницей.
2. **Словарь смещения (biasing).** Список собственных имён и терминов — имена приложений, названия проектов, «SAT», «Gemini», ваши сущности из трекера — передаётся как `initial_prompt` (Whisper) или `phrase_list` (облако). Резко повышает точность именно на тех словах, от которых зависит выполнение команды. Словарь пополняется автоматически из списка установленных приложений и названий задач.
3. **Слой нормализации сущностей в Core** (главное). Распознанное «вэс код», «vs code», «вс коде», «вэскод» приводится к канону `Code.exe` через таблицу алиасов + расстояние редактирования по фонетической нормализации. Работает независимо от того, какой STT стоит, и чинит остаточные ошибки любого провайдера.
4. **Смешанный TTS.** Ответ «Открываю VS Code» на русском не должен читаться как «ви эс цодэ». Где провайдер поддерживает SSML `<lang>` — переключаем разметкой; где нет — подставляем транскрипцию термина из той же таблицы алиасов.

### B.5 Как выбираем провайдеров — по замерам, не на глаз

В Phase M4 собираю небольшой стенд: вы наговариваете 40–60 типовых команд (ru, en и смешанные). Гоняю по всем провайдерам и меряю: WER, **точность распознавания намерения** (важнее WER — ошибка в слове «пожалуйста» безобидна, ошибка в имени приложения фатальна), задержку, стоимость. Дефолты по языкам выставляю по результатам. Стенд остаётся в репозитории — при появлении нового провайдера прогон повторяется за минуты.

### C.1 Одно следствие из «backend на VPS»

Голосовой цикл делает два сетевых перехода до VPS и обратно. Поэтому **регион VPS влияет на ощущение отзывчивости**: разница между 25 мс и 120 мс RTT — это 200 мс в общем бюджете 1.0–2.2 с.

Смягчающие факторы: STT в MVP работает **локально** (аудио по сети не идёт, уходит только текст), а вызов Gemini занимает 400–900 мс и всё равно доминирует. Так что +100 мс — это ~10 % бюджета, терпимо, но регион лучше выбрать ближе. Рекомендация: перед покупкой VPS замерьте пинг до кандидатов и возьмите вариант с RTT < 60 мс. Могу дать скрипт для замера.

Принцип «Windows не смотрит в интернет» соблюдён: агент всегда сам открывает исходящее WSS-соединение, входящих портов не слушает.
